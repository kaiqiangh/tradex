# Live PLACE absence-proof research

**Observed:** 2026-09-28
**Ticket:** [S25 follow-up — 研究 Live 未提交的充分证明](https://github.com/kaiqiangh/tradex/issues/101), under [S25 specification](https://github.com/kaiqiangh/tradex/issues/96)
**Question:** For a Live PLACE request that durably crossed `SUBMITTING`, do any currently supported provider documents define a bounded rule under which an exact order query returning no result proves that the request was never accepted, so TradeX may safely release its frozen reservation?
**Scope:** Trading 212, Binance Spot, and Bitget Classic Spot ordinary Live interfaces only. This is source research, not runtime/provider testing.

## Decision

No reviewed provider documents a maximum order-visibility delay or a bounded “not found means never accepted” rule for an ambiguous PLACE. An empty, stale, incomplete, or delayed query therefore remains inconclusive; a local timeout is not proof of provider rejection. The documented upper bounds and query omissions below make absence-based release less defensible, not more.

Binance documents one distinct, attempt-local negative response: Spot error `-2010 NEW_ORDER_REJECTED` is an error returned by the matching engine. If TradeX receives and durably binds that exact provider response to the one PLACE attempt, it is evidence that this attempt was rejected. It is not a query-absence rule, does not make a timeout or `-2013 NO_SUCH_ORDER` conclusive, and must not be generalized to arbitrary error responses. No equivalent exact rejection mapping for a Classic Spot PLACE failure is specified by the reviewed Bitget endpoint contract; Trading 212's listed error/HTTP codes likewise do not define a no-acceptance guarantee.

For the researched ambiguous-request case, retain the existing `UNKNOWN_RECONCILING` / frozen-reservation outcome and manual `KEEP_RECONCILING` path. Do not release or resend solely because a bounded query found nothing. The source set supplies no provider visibility SLA on which to base such a bound.

## Provider findings

### Trading 212 Invest API (Live)

- **Correlation identity — documented:** A successful place-order response returns a system-generated order `id`; the place request contract does not provide a client order ID that TradeX can choose in advance. The single-order endpoint is described as retrieving a *pending* order by that ID. See [Orders API](https://docs.trading212.com/api/orders/orders).
- **Query coverage and retention — documented:** The all-orders endpoint is for currently active/pending orders; it is not a complete terminal-order history. The separate [historical-orders endpoint](https://docs.trading212.com/api/historical-events/orders_1) supports cursor-based pages (up to 50 items per page) and filters such as ticker, but its contract gives no maximum history-retention period. [Pagination guidance](https://docs.trading212.com/api/section/pagination) defines page traversal, not an upper bound on record availability.
- **Consistency and visibility — documented limit:** The reviewed order and historical-order contracts publish no maximum delay from acceptance to visibility, no read-after-write guarantee, and no completeness horizon. It is an **inference** that a missing entry from these queries cannot prove non-acceptance; the provider does not state that interpretation.
- **Acceptance, timeout, and negative responses — documented:** The successful place response includes the generated ID. The endpoint documents error/HTTP responses including timeout-related status, but does not define a timeout or other listed failure as proof that matching/acceptance never occurred. The pending-by-ID endpoint documents a 404 response without assigning it a terminal-order or never-accepted meaning. Since the ID is only returned after the success response, a lost response leaves no provider-assigned ID to query exactly.
- **Assessment — inference:** No identity-plus-query sequence available in the documented contract establishes bounded absence for a lost PLACE response.

### Binance Spot (Live)

- **Correlation identity — documented:** `POST /api/v3/order` accepts caller-supplied `newClientOrderId`; `GET /api/v3/order` can query by `origClientOrderId` or `orderId`. However, Binance documents the client ID as unique only among open orders: the same ID may be accepted again after the previous order is filled. It is therefore a useful query key, not a permanent idempotency token. See [Spot Trade endpoints](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/trade).
- **Query coverage and retention — documented:** [All Orders](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/account) returns active, canceled, or filled orders, with a maximum page size of 1,000 and a maximum 24-hour `startTime`/`endTime` interval. The API marks this query as Database-sourced. It also notes that for some historical records `cummulativeQuoteQty < 0` means data is “not available at this time.” The official [Spot API error reference](https://github.com/binance/binance-spot-api-docs/blob/master/errors.md) defines `-2026 ORDER_ARCHIVED` for orders canceled or expired with zero executed quantity over 90 days ago. These details constrain query windows/availability; they do not specify a positive visibility SLA for a newly accepted order.
- **Consistency and visibility — documented:** Binance describes REST processing as asynchronous, says response delays are normal, and distinguishes data sources by potential delay. The docs state no maximum propagation/visibility time for a placed order in order-query endpoints. The inference is that no finite waiting period can turn an empty query into provider-defined proof of non-acceptance.
- **Acceptance, timeout, and exact negative responses — documented:** Binance says a 10-second backend timeout returns `-1007 TIMEOUT` with send/execution status unknown and “does not always mean” failure in the Matching Engine; it directs clients to query status. A Spot `-2013 NO_SUCH_ORDER` message is “Order does not exist,” but the docs do not say this is permanent proof the request was never accepted or provide a visibility bound. In contrast, `-2010 NEW_ORDER_REJECTED` is explicitly identified as an error returned by the matching engine. Treat only that exact, durably associated response as a direct rejection of its one request; other HTTP errors, timeouts, no-such-order responses, or later ID reuse are not equivalent. See the [Spot REST timeout guidance](https://developers.binance.com/en/docs/products/spot/rest-api) and [official Spot error codes](https://github.com/binance/binance-spot-api-docs/blob/master/errors.md).
- **Assessment — inference:** Binance enables strong correlation when a client ID is supplied and has broad order-history lookup, but an empty lookup or `-2013` after ambiguous delivery has no documented bounded absence semantics. The exact matching-engine `-2010` response is a separate narrow direct-negative evidence class, not a query rule.

### Bitget Classic Spot (Live)

- **Correlation identity — documented:** Classic Spot `POST /api/v2/spot/trade/place-order` accepts `clientOid`; a successful example returns both `orderId` and `clientOid`. `GET /api/v2/spot/trade/orderInfo` accepts either order ID or client OID. The current-order endpoint only returns unfilled orders. See the [Classic Spot Trade API](https://www.bitget.com/docs/catalog/classic-spot-trade/classic-spot-trade).
- **Query coverage and retention — documented:** The Classic Spot history-orders endpoint supports records from the past 90 days and up to 100 results per page. Separately, Bitget states that API-placed canceled-order records are retained for at most two hours on the affected “Get Historical Orders” and “Get Order Info” methods, effective 2025-02-24 UTC+8. Thus an accepted order that is later canceled can cease to be queryable well before the general history query's 90-day window. See the [official retention notice](https://www.bitget.com/support/articles/12560603823155).
- **Consistency and visibility — documented limit:** The reviewed Classic Spot endpoints publish no maximum time for a new order to appear in `orderInfo` or history, and no read-after-write or visibility SLA. An empty `data` array/no matching record is not documented as proof of non-acceptance. This is the research inference from the contract's omission, not a provider statement of a particular delay.
- **Acceptance, timeout, and exact negative responses — documented:** The place-order API documents a successful response example but no PLACE timeout semantics and no exact `orderInfo` no-match error/body meaning. The general Classic REST guide says a signed request timestamp outside 30 seconds of server time is considered expired and rejected, but the reviewed Classic Spot order endpoint does not map an exact response code/body to that condition; do not generalize it into semantics for other failures. General HTTP 400/401/403/404/429/500 meanings are too broad to establish the outcome of a durable PLACE. See the [Classic REST guide](https://www.bitget.com/docs/classic/rest-api).
- **Assessment — inference:** `clientOid` gives a useful exact correlation key, but neither current-order results nor a missing history/order-info result proves non-acceptance. The two-hour canceled-record retention rule further prevents treating a later absence as definitive.

## Limits and uncertainty

This assessment is based on the public official documentation linked above as observed on 2026-09-28; no credentials, provider API requests, or order actions were used. “Not documented” means this source review found no contractual guarantee, not that a provider could never supply one through a separate support agreement. Only provider-published, endpoint-specific visibility or rejection semantics can justify a future change to the absence rule. If such evidence is obtained, evaluate its identity binding, exact response conditions, coverage, retention, and maximum visibility delay before changing the TradeX reconciliation decision.
