## Decision supported by the research

Implement authenticated, explicitly selected known-event observations and exact selected-account broker metadata as separate evidence capabilities. Preserve the entire financial requirement: neither available corporate-action records nor a matching broker metadata entry establishes complete action coverage, historical adjustment, current account-specific unrestricted tradability, or absence of halts. The published sources below cannot supply those missing positive guarantees. Code can expose and enforce those limits; it cannot manufacture the missing provider contract.

The next single ticket can deliver that observable vertical slice with deterministic blocking and exact provenance. Its completion must not close the parent prerequisite or positive approval/Prepare/dispatch criteria. Those criteria require genuinely supported authoritative evidence or an explicitly approved normative contract decision; no such revision is approved here.

### Alpaca known corporate-action records

The [REST contract](https://docs.alpaca.markets/us/reference/corporateactions-1) uses GET `https://data.alpaca.markets/v1/corporate-actions`; its sandbox data host is distinct from Paper trading. Authenticate selected saved credentials explicitly; calendar success proves no data-host entitlement. `start`/`end` inclusively filter **process_date**, not announcement/effective dates. `data_quality=all` includes early incomplete records; default `complete` can still return incomplete already-processed records. Upstream acquisition/processing delays have no creation-time guarantee. Limit1–1000 is total records; follow `next_page_token` to exhaustion. Response wraps grouped `corporate_actions` plus nullable token. Documented statuses200/400/401/403/429/500 require explicit unavailable/quota handling.

Brief [schema mappings](https://docs.alpaca.markets/us/reference/corporateactions-1.md): provider UUID `id` → event identity; symbol/old-new symbols and optional security identifiers → canonical matching; `process_date` → processing date; split/dividend `ex_date` or merger/reorganization `effective_date` → date-only economic field; ratio/rate → exact-decimal event detail. `name_change` and `worthless_removal` do not supply an effective timestamp. No REST creation/update/announcement timestamp is defined. Preserve missing/partial dates; never invent midnight UTC, equate process date with announcement, or label worthless removal as delisting.

The sixteen groups cover forward/reverse/unit splits; cash/stock dividends; spin-offs; cash/stock/mixed mergers; redemption; name change; worthless removal; rights distribution; partial call; reorganization; capital-gains distribution. Keep unsupported categories visible or explicitly unsupported rather than silently discard them. The [May additions](https://docs.alpaca.markets/us/v1.1/changelog/2026-05-22-corporate-actions-5c87d2b) added reorganizations/partial calls; [June changes](https://docs.alpaca.markets/us/changelog/2026-06-03-market-data-9dddd18) added region/ISIN/currency; [August changes](https://docs.alpaca.markets/us/changelog/2026-08-27-capital-gains-distributions-fce488a) added capital-gains distributions. This warrants a typed wire extension rather than pretending the existing four-category/time-only payload covers the provider contract.

**Inference:** exhausted pagination proves completion only of that returned process-date query. Empty or absent groups cannot establish no recently announced/upcoming action; late processing and changes outside a bounded window remain possible. Date-only events need date semantics on the wire. Historical adjustment remains separately UNAVAILABLE/UNVERIFIED until actual history provenance proves it.

The [SSE contract](https://docs.alpaca.markets/us/reference/subscribetocorporateactionseventssse) offers `stream.data.alpaca.markets/v1beta1/events/corporate-actions`, insert/update/delete mutations, region/type filters and inclusive replay by timestamp/ULID or Last-Event-Id. Envelope `event_id` identifies a mutation; `ca.id` identifies the action; `at` is emission time, not announcement/effective time. Decimal fields are strings. It shares the REST dataset. A later stream producer can manage revisions/deletions but cannot cure upstream completeness delays; subscribe acknowledgment alone is not a current per-instrument initial-state snapshot. Do not silently replace bounded REST work with an unaccepted SSE capability or entitlement.

### Trading 212 exact instrument metadata

The [official API overview](https://docs.trading212.com/api) limits the API to Invest/Stocks ISA, uses authenticated requests and separate Live/Demo hosts, applies quotas per account, and states API execution uses primary account currency. User selection here is Live; do not fall back to Demo.

The [complete OpenAPI](https://docs.trading212.com/_bundle/api.json?download=) supplies:

| Fixed Live GET | Defined response / limits |
|---|---|
| `/api/v0/equity/metadata/instruments` | Array: ticker, type, ISIN, currencyCode, name/shortName, addedOn, maxOpenQuantity, workingScheduleId, extendedHours. Data refreshed10minutes;1request/50seconds. |
| `/api/v0/equity/metadata/exchanges` | Array: exchange id/name, workingSchedules{id,timeEvents{date,type}}. Schedule events: OPEN/CLOSE/BREAK_START/BREAK_END/PRE_MARKET_OPEN/AFTER_HOURS_OPEN/AFTER_HOURS_CLOSE/OVERNIGHT_OPEN. Refreshed10minutes;1request/30seconds. |

Both declare200/401/403/408/429;403 means metadata scope missing. Neither is paginated in its operation schema. No required-field list, MIC, provider observation timestamp, current halt/restriction flag, account identity or discontinued field exists. `maxOpenQuantity` has no semantic description. Treat presence as account-authenticated accessible metadata, never full current unrestricted tradability; do not infer direction-specific permission from zero/absence.

The account summary separately supplies id/currency. Bind same selected credential/version and compare that remote identity to the saved account before accepting metadata. Match unique exact ticker, STOCK, USD and validated identity; join workingScheduleId uniquely. A name/schedule ID alone cannot verify MIC XNAS. Local symbol mappings need conflict handling and security-identity corroboration; do not auto-remap after symbol changes.

Deprecated Pie details expose per-instrument `InstrumentIssue` restrictions, including suspension, delisting, no-longer-tradable and position/test restrictions. They are contextual to existing Pie instruments; no complete selected-account tradability/halts endpoint exists among the22 operations. Paid dividend history is retrospective account activity, not prospective complete corporate-action coverage. These conclusions come from enumerating the [whole bundle](https://docs.trading212.com/_bundle/api.json?download=), not from a failed endpoint search. Do not create/change a Pie or probe orders to obtain evidence.

Trading 212 documents [instrument suspensions](https://helpcentre.trading212.com/hc/en-us/articles/360007293218-Why-might-trading-in-a-specific-instrument-be-suspended-unavailable) for compliance, regulatory and exchange reasons. **Inference:** broker restrictions can differ from public exchange status and static catalog membership. Metadata refreshed ten minutes ago cannot acquire realtime quality merely because TradeX received it just now.

### Other published capabilities and licensing limits

Alpaca's [stock status channel](https://docs.alpaca.markets/us/docs/real-time-stock-pricing-data) publishes symbol, status/reason codes, provider timestamp and tape; UTP distinguishes halt, pause, quotation resumption and trading resumption. Access depends on subscription, with production access guidance to contact sales. It can supply exchange-status evidence if actually supported/entitled and correctly scoped; quotation resumption is not trading resumption. It cannot certify selected Trading 212 account restrictions. Existing quote streaming consumes quotes, not a complete status producer. No new purchase/provider/source is implicitly selected by this research.

The [deprecated Alpaca announcements endpoint](https://docs.alpaca.markets/us/reference/get-v2-corporate_actions-announcements-1) points to the new corporate-action endpoint. Reintroducing it is not a supported completeness workaround. [Market Data FAQ](https://docs.alpaca.markets/us/docs/market-data-faq) distinguishes latest unadjusted data from historical adjustment behavior; event downloads cannot change DuckDB history provenance.

The [Alpaca terms linked by its OpenAPI](https://s3.amazonaws.com/files.alpaca.markets/disclosures/library/TermsAndConditions.pdf) describe personal/noncommercial use, additional subscriber agreements and restrictions on publication/distribution. No corporate-action-specific local-retention duration or jurisdiction entitlement was established by these reviewed sources. The [CUSIP change notice](https://docs.alpaca.markets/us/v1.1/changelog/cusip) warns some items require additional licenses. OpenAPI document licensing is not a market-data license. Recommendation: metadata configuration/audit hashes plus process-scoped event observations; do not claim arbitrary archival/export/redistribution rights.

Trading 212 [API Terms](https://www.trading212.com/legal-documentation/API-Terms_EN.pdf), last-published date17.10.2025 in the current PDF, restrict third-party distribution and describe personal/testing access and consent for applications/custom interfaces. They state API orders use its **Systematic Internaliser** (§3.4), and supplied market data is not realtime (§7.1). **Inference:** XNAS in TradeX is verified listing/calendar identity, not proof of actual broker execution venue. Preserve that distinction in the next spec; do not change an execution-venue invariant without explicit approval. Provider usage authorization and market-data rights remain separate from TradeX account permission verification.
