# S29.8 — 以精确容量与时段额度输入履行 Binance Spot Live PLACE 拥有方资格

父项：[验证 Binance Spot Live 可信执行](https://github.com/kaiqiangh/tradex/issues/121)。实现/复审起始基线 `dev@dd1d5c91020fb3c12b62e5cded5614760d8df11a`。[English](s29-owning-place-qualification-spec.md)。仅规划；尚未实施与验收。

## 问题陈述

三个只读来源切片现已暴露 Binance Spot 的精确账户容量库存、其声明的 ORDERS 时段定义与计数，以及不可变 Proposal 的执行规则。但它们只是作为证据展示：拥有方 Live PLACE 路径仍然只依据已保存账户余额中提供方声明的 available/committed 数字推导容量。拥有方门禁不消费声明的开放订单库存、标的范围敞口或时段额度，因此用户无法判断一笔订单此刻是否真会被接纳，而且即使交易所自身的下单频率窗口已经用尽、或容量证据只部分完整，Prepare 仍可能成功。读取证据页面不改变拥有方门禁的判定，使已交付的输入沦为装饰而非权威。

## 解决方案

让现有面向普通 Binance Spot Live 账户的拥有方 Live PLACE 资格判定，以与只读切片相同的精确性与失败关闭纪律，真正消费已交付的容量与时段额度证据。用户看到的是一个精确、当前、有界于已复核意图的陈述：交易所此刻会接纳多少、哪些声明事实构成边界、以及唯一的阻塞原因是什么；当该陈述当前不可用时，Prepare 直接拒绝。此处不授予 Arm、consent、派发或任何新的执行权。

## 用户故事

1. 作为用户，我希望我的 Binance Spot Live 容量资格完全由交易所自己声明的数字推导，从而我自己的算术永远无法臆造可用量。
2. 作为用户，我希望「Free/Locked 余额读取」与「声明的开放订单库存」被区分，从而订单锁定不会被重复扣减。
3. 作为用户，我希望资格绑定到精确的不可变 Proposal、账户、标的、规则材料与来源代际，从而他人的证据无法为我的意图定性。
4. 作为用户，我希望不完整或分类未完成的开放订单覆盖被视为不可用，从而被截断的库存不会被误认为空闲容量。
5. 作为用户，我希望标的范围的开放买单数量只用于敞口完整性，从而它绝不会被暗中当作可用余额。
6. 作为用户，我希望声明的 ORDERS 时段上限与当前计数被精确比较，从而小数或整数表示不会把已用尽的窗口四舍五入成可用。
7. 作为用户，我希望已用尽或未知的时段窗口阻塞 Prepare，从而交易所侧限频不会靠一笔被拒订单才被发现。
8. 作为用户，我希望时段计数完全保持提供方上报的原值，从而任何本地递减、重置或窗口滚动假设都不会凭空造出空闲额度。
9. 作为用户，我希望这些计数的本地时间关联被明确标注为不确定，从而推断出的瞬时值绝不会被展示为提供方计数时间戳。
10. 作为用户，我希望在余量为零或未知时给出唯一的绑定阻塞原因，从而我知道该修什么而不是靠猜。
11. 作为用户，我希望过期、失败、退役或版本变更的容量与时段证据使资格关闭失败，从而昨天的余量无法授权今天的订单。
12. 作为用户，我希望我自己的在途预留仍属 TradeX 的职责、交易所声明的数字仍属交易所，从而提供方读取不会释放本地预留、本地预留也不会改写提供方真相。
13. 作为用户，我希望并发的相同意图按账户互相隔离，从而一次尝试无法消耗另一次尝试的余量。
14. 作为用户，我希望现有的百分比与名义金额风险检查、精确申报价检查与 PRICE_RANGE 解释被保留，从而本切片不会削弱任何已被强制执行的约束。
15. 作为用户，我希望拥有方资格恰好拒绝不可变审批会授权的同一个意图，从而审批与准入不会互相矛盾。
16. 作为用户，我希望捕获与 pre-arm 复核展示当时真正被依赖的资格且不续期，从而使已保存的评估保持诚实。
17. 作为用户，我希望随后的 get、refresh 或重开无法为已捕获的资格续期，从而使历史不会变成新鲜授权。
18. 作为用户，我希望精确的容量单位（买单为 QUOTE、卖单为 BASE）与数字一同给出，从而 USDT 绝不会被当作 USD 读取。
19. 作为用户，我希望键盘与 1280/768/390 复核中阻塞原因与数字同样醒目，从而使金融同意保持审慎。
20. 作为复核者，我希望有真实的公开 RED/GREEN、精确来源检查、普通构建与独立串行 Standards → Spec 证据，从而任何标签或仅 fixture 的投影都不能确立本切片。

## 实现决策

- 仅对普通 Binance Spot Live 账户扩展既有拥有方 Live PLACE 路径（风险判定 → 不可变审批 → Prepare → 已认证子 Gateway）。不引入并行权威模型、不新增第二套容量投影、不新增账户或来源配置，也不接受渲染器提供的金额、标的、计数、上限或资格。
- 拥有方资格按绑定身份消费已交付的精确账户容量证据与时段额度证据（workspace、Proposal、Proposal hash、账户、标的、BASE/QUOTE、规则材料版本、来源代际与 state version）。其中任一项不匹配即退役证据，而不是靠假设去调和。
- 提供方声明的 `free` 已排除订单锁定。因此声明的开放订单库存用于证明覆盖完整性并交叉核对声明的 locked 数字，绝不从 `free` 二次扣减。两个声明来源相互矛盾时为不可用，而不是静默偏向其中之一。
- 声明的 ORDERS 时段上限与计数用现有十进制辅助函数精确比较。剩余准入额度是推导值、不落盘；计数绝不本地递减、重置或向前滚动，也绝不假设窗口边界已越过。
- 时段计数不带提供方时间戳。既有的保守本地时间关联是唯一的时间陈述；无法证明仍处于原窗口内的关联使该额度不可评估。
- 任何分类不完整、订单覆盖不完整、order list 覆盖不完整、未决义务、失败读取、非原子采集、缺失提供方时间、证据过期或版本变更，都以待 `RISK_EVIDENCE_UNAVAILABLE` 语义使拥有方资格失败关闭，而不是给出一个更小的数字。
- TradeX 自身的预留台账仍是并发本地尝试的权威，提供方声明证据仍是交易所已持有内容的权威。两者不得互相改写；既有幂等预留释放、撤防与策略变更行为原样保留。
- 复用既有容量时效窗口、响应/规则/字段/十进制/槽位边界、固定普通公开主机、拒绝重定向、IP 预算与冷却，不做放宽。不下探针订单、不变更来源、不重置 HTTP 权重、不在提供方 I/O 期间持有 Control Plane 锁。
- 该路径的容量投影新增显式的可用来源与已承诺来源，使 UI 能指明每个数字的声明出处；唯一绑定阻塞是类型化原因而非自由文本。其他提供方保持其现有来源不变。
- 即使所有数字都当前可用，拥有方资格仍保持执行未获资格：它不是成交承诺、不是未来 taker 阶段的准入保证，也不能替代费用、所需 FX、即时认证 preflight 或私有流就绪。这些仍是独立的拥有方工作。
- 实际当前、捕获与 pre-arm React 视图解释该资格、其声明出处、其阻塞与未来不确定性，并给出显式恢复路径，保留冻结捕获与「捕获内不可刷新」规则。键盘 1280/768/390 与配对的中英金融/线缆/证据契约仍为必需。原型代码保持不变。

## 测试决策

使用现有公开的账户/来源/草稿/Proposal/规则/容量/时段/风险/审批/Prepare 流程与真实 React，仅把外部 HTTP/vault 生产者置为假。为每项新增的拥有方行为先记录真实公开 RED 再 GREEN。

在公开接缝验证：完整且当前的声明容量恰好接受可用额度；多一个单位即被拒绝；分类不完整、订单/list 覆盖不完整与未决义务失败关闭；locked 数字与声明的开放订单库存相矛盾时失败关闭；买单使用 QUOTE、卖单使用 BASE 并标注单位；已用尽的时段窗口阻塞 Prepare；仅剩一个额度时接受一次并拒绝第二次；未知、畸形或非整数计数与上限失败关闭；无法证明仍处于原窗口内的时段关联使额度不可评估；并发 prepare 下按账户隔离；提供方声明证据绝不释放本地预留；pending、失败、绑定变更、规则材料变更、来源代际变更、重开、过期与更新所有者结果退役该资格；随后的 get 或 refresh 绝不为已捕获资格续期；且每个正向用例仍不具备 Arm、consent、派发或任何新权限。

在键盘 1280/768/390 下重放实际当前、捕获与 pre-arm 视图，以及代表性拒绝与恢复路径，确认无溢出。

要求当前全量与受影响的规则/容量/时段/Hot/Gateway 套件、生成的 IPC 与配对追溯、普通桌面构建与 pin、独立串行 Standards → Spec 复审，以及精确的源码/证据/远端/跟踪器交付。原生、提供方、金融、物理、原型与 main 证据保持单独标注且不声明。
