# S29.8 — 以精确容量与时段额度输入履行 Binance Spot Live PLACE 拥有方资格

父项：[验证 Binance Spot Live 可信执行](https://github.com/kaiqiangh/tradex/issues/121)。实现/复审起始基线 `dev@dd1d5c91020fb3c12b62e5cded5614760d8df11a`。[English](s29-owning-place-qualification-spec.md)。仅规划；尚未实施与验收。

## 问题陈述

三个只读来源切片现已暴露 Binance Spot 的精确账户容量库存、其声明的 ORDERS 时段定义与计数，以及不可变 Proposal 的执行规则。但它们只是作为证据展示：拥有方 Live PLACE 路径仍然只依据已保存账户余额中提供方声明的 available/committed 数字推导容量。拥有方门禁不消费声明的开放订单库存、标的范围敞口或时段额度，因此用户无法判断一笔订单此刻是否真会被接纳，而且即使交易所自身的下单频率窗口已经用尽、或容量证据只部分完整，Prepare 仍可能成功。读取证据页面不改变拥有方门禁的判定，使已交付的输入沦为装饰而非权威。

## 解决方案

让现有面向普通 Binance Spot Live 账户的拥有方 Live PLACE 资格判定，以与只读切片相同的精确性与失败关闭纪律，真正消费已交付的容量与时段额度证据。用户看到的是一个精确、当前、有界于已复核意图的陈述：交易所此刻会接纳多少、哪些声明事实构成边界、以及唯一的阻塞原因是什么；当该陈述当前不可用时，Prepare 直接拒绝。此处不授予 Arm、consent、派发或任何新的执行权。

## 用户故事

1. 作为用户，我希望我的 Binance Spot Live 容量资格完全由交易所自己声明的数字推导，从而我自己的算术永远无法臆造可用量。
2. 作为用户，我希望「Free/Locked 余额读取」与「声明的开放订单库存」被区分，从而订单锁定不会被重复扣减。
3. 作为用户，我希望资格绑定到精确的不可变 Proposal、账户、标的、规则材料与来源代际，从而他人的证据无法为我的意图定性。
4. 作为用户，我希望不完整或分类未完成的开放订单覆盖被视为不可用，从而被截断的库存不会被误认为空闲容量。
5. 作为用户，我希望标的范围的开放买单数量只用于敞口完整性，从而它绝不会被暗中当作可用余额。
6. 作为用户，我希望声明的 ORDERS 时段上限与当前计数被精确比较，从而小数或整数表示不会把已用尽的窗口四舍五入成可用。
7. 作为用户，我希望已用尽或未知的时段窗口阻塞 Prepare，从而交易所侧限频不会靠一笔被拒订单才被发现。
8. 作为用户，我希望时段计数完全保持提供方上报的原值，从而任何本地递减、重置或窗口滚动假设都不会凭空造出空闲额度。
9. 作为用户，我希望这些计数的本地时间关联被明确标注为不确定，从而推断出的瞬时值绝不会被展示为提供方计数时间戳。
10. 作为用户，我希望在余量为零或未知时给出唯一的绑定阻塞原因，从而我知道该修什么而不是靠猜。
11. 作为用户，我希望过期、失败、退役或版本变更的容量与时段证据使资格关闭失败，从而昨天的余量无法授权今天的订单。
12. 作为用户，我希望我自己的在途预留仍属 TradeX 的职责、交易所声明的数字仍属交易所，从而提供方读取不会释放本地预留、本地预留也不会改写提供方真相。
13. 作为用户，我希望并发的相同意图按账户互相隔离，从而一次尝试无法消耗另一次尝试的余量。
14. 作为用户，我希望现有的百分比与名义金额风险检查、精确申报价检查与 PRICE_RANGE 解释被保留，从而本切片不会削弱任何已被强制执行的约束。
15. 作为用户，我希望拥有方资格恰好拒绝不可变审批会授权的同一个意图，从而审批与准入不会互相矛盾。
16. 作为用户，我希望捕获与 pre-arm 复核展示当时真正被依赖的资格且不续期，从而使已保存的评估保持诚实。
17. 作为用户，我希望随后的 get、refresh 或重开无法为已捕获的资格续期，从而使历史不会变成新鲜授权。
18. 作为用户，我希望精确的容量单位（买单为 QUOTE、卖单为 BASE）与数字一同给出，从而 USDT 绝不会被当作 USD 读取。
19. 作为用户，我希望键盘与 1280/768/390 复核中阻塞原因与数字同样醒目，从而使金融同意保持审慎。
20. 作为复核者，我希望有真实的公开 RED/GREEN、精确来源检查、普通构建与独立串行 Standards → Spec 证据，从而任何标签或仅 fixture 的投影都不能确立本切片。

## 实现决策

- 仅对普通 Binance Spot Live 账户扩展既有拥有方 Live PLACE 路径（风险判定 → 不可变审批 → Prepare → 已认证子 Gateway）。不引入并行权威模型、不新增第二套容量投影、不新增账户或来源配置，也不接受渲染器提供的金额、标的、计数、上限或资格。
- 拥有方资格按绑定身份消费已交付的精确账户容量证据与时段额度证据。workspace、Proposal、Proposal hash、账户、标的、BASE/QUOTE、规则材料版本与来源代际在两个输入之间互相比较，其中任一项不匹配即退役证据，而不是靠假设去调和。state version 刻意以不同方式参与：每个输入自身的 state version 已由产出它的已交付切片按其自身预期游标强制校验，随后两者再被折叠进本资格产出的两个证据版本摘要，使该陈述指明它所依据的精确观测状态。两个输入的 state version 之间绝不互比相等，因为它们各自是不同端点观测的内容摘要，两个这样的摘要不可能相等；要求相等会连一个完全当前且合格的意图都一并阻塞，而不是退役陈旧证据——这与失败关闭恰好相反。
- 提供方声明的 `free` 已排除订单锁定。因此声明的开放订单库存只用于证明覆盖完整性；声明的 `free`/`locked` 数字按原值上报，既不二次扣减，也不与标的范围的开放买单数量互相轧差。不对「资产级 locked 数字」与「标的范围库存」断言矛盾，因为资产锁定有开放订单之外的既定成因；断言矛盾会是不严谨的，而非失败关闭。
- 声明的 ORDERS 时段上限与计数用现有十进制辅助函数精确比较。剩余准入额度是推导值、不落盘；计数绝不本地递减、重置或向前滚动，也绝不假设窗口边界已越过。
- 时段计数不带提供方时间戳。既有的保守本地时间关联是唯一的时间陈述；无法证明仍处于原窗口内的关联使该额度不可评估。
- 任何分类不完整、订单覆盖不完整、order list 覆盖不完整、超出两条固定出处标签之外的任何未决容量义务、观测缺失/失败/过期/退役，或版本变更，都以待 `RISK_EVIDENCE_UNAVAILABLE` 语义使拥有方资格失败关闭，而不是给出一个更小的数字。已交付切片的固定标签——容量切片的非原子与执行未获资格标记，以及时段切片的计数时间戳、窗口关联与执行未获资格标记——描述的是证据如何取得，而非它未能覆盖什么。它们被原样载入 `carriedLimitations`，绝不自我升级为第二重隐藏准入否决，因为任何公开接缝上的观测都必然带有它们。
- TradeX 自身的预留台账仍是并发本地尝试的权威，提供方声明证据仍是交易所已持有内容的权威。两者不得互相改写；既有幂等预留释放、撤防与策略变更行为原样保留。
- 复用既有容量时效窗口、响应/规则/字段/十进制/槽位边界、固定普通公开主机、拒绝重定向、IP 预算与冷却，不做放宽。不下探针订单、不变更来源、不重置 HTTP 权重、不在提供方 I/O 期间持有 Control Plane 锁。
- 唯一绑定阻塞是类型化原因而非自由文本；该资格为它上报的每个数字标明声明出处，使读者无需推测某个数字出自哪一次交易所读取。这两类出处分别是开放订单与余额库存读取（`PROVIDER_DECLARED_OPEN_ORDERS`）与订单速率计数读取（`PROVIDER_DECLARED_ORDER_RATE_COUNTERS`）。已消费的容量投影刻意保持不变，而不是为其扩展逐数字的可用来源与已承诺来源：PRD 要求本陈述由那些已交付的只读观测推导、绝不来自第二套投影，且本切片原样继承已消费切片的行为而非重塑它们。其他提供方保持其现有来源不变。
- 即使所有数字都当前可用，拥有方资格仍保持执行未获资格：它不是成交承诺、不是未来 taker 阶段的准入保证，也不能替代费用、所需 FX、即时认证 preflight 或私有流就绪。这些仍是独立的拥有方工作。
- 生成的线缆契约必须恰好容纳本契约实际产出的值。React 在任何组件读取之前先用生成的校验器解码每个响应，因此声明的字符串长度若比实际产出的值更窄，就会让整条陈述在应用内无法解码——即便普通 Rust 套件全部通过。因此两个绑定证据版本按 `sha256:` 摘要的 71 个字符声明（与 `proposal_hash` 一致），而不是更短的长度。这由浏览器重放发现，记录于 `evidence/s29-owning-place-qualification/ui-contract-red.txt`。
- 实际当前、捕获与 pre-arm React 视图解释该资格、其声明出处、其阻塞与未来不确定性，并给出显式恢复路径，保留冻结捕获与「捕获内不可刷新」规则。键盘 1280/768/390 与配对的中英金融/线缆/证据契约仍为必需。原型代码保持不变。

## 测试决策

使用现有公开的账户/来源/草稿/Proposal/规则/容量/时段/风险/审批/Prepare 流程与真实 React，仅把外部 HTTP/vault 生产者置为假。为每项新增的拥有方行为先记录真实公开 RED 再 GREEN。

在公开接缝验证：完整且当前的声明库存与时段集合为该意图定性，给出由最紧的声明桶推导出的精确剩余下单额度并指明绑定桶；随着交易所自身计数推进，该额度恰好降到 1、再降到 0；声明的 ORDERS 时段缺少对应计数器、计数超过其声明上限、交易所自身分类无法归类的订单行、以及全新意图没有任何绑定时段观测，各自以唯一类型化阻塞失败关闭；声明的 `free`、`locked` 与开放买单数量按原值上报，不轧差、不二次扣减；买单使用 QUOTE、卖单使用 BASE 并标注单位；已用尽的声明窗口使审批不合格；以及本地关联无法再证明仍处于原窗口内的时段退役计数器、使额度不可评估；且每个正向用例仍不授予 Arm、consent、派发或任何新权限。已消费切片的退役、过期、pending/失败、绑定、规则材料、来源代际、重开、更新所有者与按账户隔离行为，以及「提供方读取绝不释放本地预留」规则，均原样继承并继续由已交付的容量、时段与预留套件覆盖；本切片不得削弱它们，也绝不为已捕获资格续期。

在键盘 1280/768/390 下重放实际当前、捕获与 pre-arm 视图，以及代表性拒绝与恢复路径，确认无溢出。通过真实应用到达正向用例与唯一类型化阻塞，要求外部生产者能够声明一份完全覆盖的库存，以及（另一次）一份已达其声明上限的订单速率计数器；两者都是外部 HTTP 生产者状态，因此由 fixture 接缝新增，不为到达任何一者而放宽产品断言或 Control Plane 取值。

要求当前全量与受影响的规则/容量/时段/Hot/Gateway 套件、生成的 IPC 与配对追溯、普通桌面构建与 pin、独立串行 Standards → Spec 复审，以及精确的源码/证据/远端/跟踪器交付。原生、提供方、金融、物理、原型与 main 证据保持单独标注且不声明。

真实 Binance 费用与真实所需执行级 FX 输入、参考价流式、即时认证执行 preflight、执行过期与私有流生命周期实现、超出消费既有审批的不可变金融意图变更、超出既有已批准门禁的实际订单/探针/Arm/consent、新增账户或来源配置、权利授予、S28/Testnet/Bitget 范围变更、物理 S27 休眠豁免、原型修复与 main 合并。这些仍是后续拥有方工作，未被豁免。

## 补充说明

2026-10-09 复核的主要契约：[限频与下单计数限制](https://raw.githubusercontent.com/binance/binance-spot-api-docs/master/rest-api.md#rate-limits)、[当前开放订单](https://raw.githubusercontent.com/binance/binance-spot-api-docs/master/rest-api.md#current-open-orders-user_data)、[账户信息](https://raw.githubusercontent.com/binance/binance-spot-api-docs/master/rest-api.md#account-information-user_data)。Binance 在响应信封中以原始整数上报时段计数，并把 `ORDERS` 记录为按账户的下单限频；把未知或不完整的读取当作可用是本规范明确的拒绝设计，而非提供方保证。

实际技术依赖是已完成的精确账户容量输入与时段额度输入；已完成的 Proposal 规则/参考切片提供本资格所依据的标的规则。完整父项、map、S28、S17、物理 S27 与 main 门禁保持 OPEN。既有的粒度与接缝批准继续适用；不重复询问。

规范更正（2026-10-09，验收前）：本规范首次发布的草稿把已消费切片的固定出处标签（非原子采集、缺失提供方计数时间戳、执行未获资格）列为准入缺口，并断言「资产级 locked 数字」与「标的范围库存」之间存在矛盾检查。二者都经不起与已交付证据的对照：容量切片始终携带 `NON_ATOMIC_PROVIDER_SNAPSHOT` 与 `DYNAMIC_INPUTS_NOT_EXECUTION_QUALIFIED` 且 `atomic: false`，时段切片始终携带其三条对应标签，而标的范围开放买单数量与标的开放订单计数由同一批行计算得出，因此该矛盾不可表达。把标签当作致命项会使准入问题在任何公开接缝上永久无法回答，而断言该矛盾则是不严谨的。据此更正实现决策 3、6 与测试决策第二段；已交付标签现按原值载入 `carriedLimitations`，致命集合恰为「未知覆盖」。
