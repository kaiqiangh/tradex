## Problem Statement

Trade can show bounded exact-account open-order inventory but cannot show authenticated account-wide unfilled-order interval usage. Open inventory, successful-order headers and local request-weight counters answer different questions. Users need the actual interval definitions and original current-account counter observations before an owning evaluator can reason about a new ordinary Market/Limit request; no observed count or old collection should be mistaken for available execution capacity.

## Solution

For an existing immutable ordinary Binance Live BTC/USDT or ETH/USDT Proposal, explicitly collect the actual required order-rate definitions and authenticated exact-account interval counters, then explain original count/limit/interval units, coverage, read windows, provenance, age, failure/recovery and unresolved temporal execution qualification in current and captured/pre-arm review. Keep open-order filter counts, interval usage, HTTP request budgets and local reservations separate. This complete read-only input slice precedes owning dynamic qualification and immediate authenticated preflight; it does not place, probe, reserve, arm or approve.

## User Stories

1. As a user, I want interval inputs bound to my immutable Proposal and saved ordinary account, so that another account or environment cannot supply my quota observation.
2. As a user, I want the backend to derive account UID/key ownership and required reads, so that the renderer cannot invent identity, counters or authority.
3. As a user, I want actual ORDERS interval definitions, so that remembered limits or a different rate-limit category cannot become my current limit.
4. As a user, I want a bounded response for every actually declared interval, so that a missing interval is not silently treated as unlimited.
5. As a user, I want account-wide scope across keys/IPs/APIs stated, so that switching keys or workspaces cannot reset usage.
6. As a user, I want original exact integers retained as strings, so that large counts and limits cannot lose precision in the browser.
7. As a user, I want zero observed usage distinguished from missing usage, so that incomplete data cannot appear as zero orders.
8. As a user, I want original count and limit kept even at or above a limit, so that projection does not clamp away provider truth or certify remaining capacity.
9. As a user, I want open-order inventory and interval unfilled-order counters clearly separated, so that one cannot substitute for the other.
10. As a user, I want fill/cancel effects described only under the official counter contract, so that local fill/cancel observations cannot invent decrement credit or reset an interval.
11. As a user, I want unknown interval/type/active fields and contradictory limits marked unresolved, so that a guessed schedule cannot create qualification.
12. As a user, I want read windows and original provider clock samples separated from counter snapshot time, so that a receipt or clock does not impersonate a provider counter watermark.
13. As a user, I want expiry and possible UTC-boundary crossing to retire current observations conservatively, so that cached usage is not presented as a new interval's counter.
14. As a user, I want explicit refresh with sanitized auth/time/quota/failure recovery, so that failures clear current inputs and do not expose my key or retain false success.
15. As a user, I want account/key/source/rule/market/policy/Proposal/workspace/session/time changes and late results rejected, so that old counters cannot attach to new intent.
16. As a user, I want saved review to retain approved bounded observations/digests without refresh or receipt renewal, so that history stays the reviewed assessment.
17. As a user, I want keyboard and1280/768/390 explanations, so that interval scope, temporal uncertainty and independent blockers remain readable.
18. As a reviewer, I want genuine public RED/GREEN, exact-byte checks/build/UI and serial Standards then Spec, so that this prerequisite cannot be closed by a hidden financial snapshot seed or an unrelated success label.

## Implementation Decisions

- Reuse the immutable Proposal context, saved ordinary Binance connection, trusted-clock/runtime bindings, signed/vault/zeroization boundary, P3 read scheduler and current/captured review modules. Add trusted local get and explicit CAS refresh identified only by workspace, stored Proposal and current state version. No new account/source setup, renderer URL/symbol/UID/interval/count/limit/time/authority payload or background scan.
- Backend derives canonical BTC/ETH/USDT context and exact saved account/remote UID/credential version, plus workspace/source/rule material/market/policy/Proposal/hash/session/clock generations. All refresh ownership and publication checks remain at the existing trusted main consumer; integration stdio remains an explicitly isolated build seam. Local get is read-only and never calls vault/providers.
- Obtain actual definitions through one fixed public ordinary exchangeInfo request filtered to the derived canonical symbol, not a metadata universe scan. Parse its bounded rateLimits terms; actual ORDERS definitions establish the requested account-interval coverage. REQUEST_WEIGHT/RAW_REQUESTS are separate transport constraints, not order quota. Missing or unknown definitions remain explicit; do not infer unlimited capacity or make unnecessary private reads when no genuine defined purpose can be established.
- Use fixed ordinary public clock and signed USER_DATA account identity then rateLimit/order GETs. Verify original numeric Spot UID equals the saved exact account before accepting private counters; no balance/order/list/history read is added for this purpose. Proposed current costs: public clock1 and filtered exchangeInfo20 on shared IP only; authenticated account20 and rateLimit/order40 on actual signed UID/IP. Recheck primary contracts during implementation. Reuse HMAC/recvWindow5000 and fixed-host/no-redirect safeguards, never fabricate a UID for public reads.
- Compare declared and observed interval tuples/limits from original responses. Known units are SECOND/MINUTE/HOUR/DAY, with original positive intervalNum and original nonnegative limit/count, bounded at signed64-bit and preserved as exact decimal strings (max20). Duration multiplication is checked, never floating point. Zero limit is retained as reported, not reinterpreted as disabled; count at/above limit stays original. Duplicate fields/tuples, original floats/strings masquerading as integers, negative/overflow, malformed/oversized/contradictory responses fail or remain specifically incomplete; never drop rows to produce complete coverage. Proposed limits:512KiB per response,32 interval rows and8 transient Proposal slots. Unknown types/units/active fields remain bounded unresolved evidence.
- The counter endpoint reports account-wide interval usage, not the open-order filter inventory or a per-symbol capacity. No local fills/cancellations/expiry, header absence or workspace/key/source change can decrement/reset the observed counter. Preserve actual provider cooldowns/418/429 Retry-After and UID/IP caps, and never conflate HTTP read budgets with placement interval limits. No order test, PLACE/CANCEL/amend/listen-key mutation or lifecycle probe.
- Typed observations expose declaration and private read digests/windows, exact interval tuples/counts/limits, bounded completeness/unknown reasons, first receipts and original clock samples. Aggregate counter providerObservedAt is absent when not supplied; separate reads are non-atomic. Do not manufacture provider resetAt, counter snapshot time, remaining slots or an execution-qualified interval identity. Any time-window association inferred from clock/definitions is explicitly derived, with uncertainty and conservative possible-boundary retirement; it is not an original provider counter timestamp or admission promise.
- Overall refresh deadline30s, bounded vault worker and existing12-second completion margin. No CP lock spans vault/network work. Pending refresh immediately retires old current success; failed or expired reads clear current observations while retaining sanitized explanation. Source/binding/ownership sequence changes, late completion, reopen and clock/session resets cannot publish or revive old evidence. Cached get/history never renew first receipts. Age obeys the stricter of30s and the configured stale threshold, and possible interval rollover may retire sooner.
- Input qualification always remains UNAVAILABLE with a specific not-execution-qualified reason. An owning evaluator must later combine applicable plain-intent filter contributions, actually required interval admission, local reservations, authenticated immediate preflight and all other financial duties. This input slice does not upgrade complete rules, rights/quote/liquidity, permissions/health, funding/fees/FX, Arm, consent, Prepare or Gateway. Existing exact CANCEL/reconciliation remain independent.
- Current Trade and captured RiskDecision/history/pre-arm explain all units and separate budget concepts, original versus derived time, coverage/uncertainty/age/fault/recovery and unavailable qualification. Only approved bounded aggregate observations/digests persist; no raw account/rate-definition/counter response, secret or runtime cache. Captured review has no refresh/polling controller. Synchronize English/Chinese financial, IPC, interaction and evidence contracts during implementation.
